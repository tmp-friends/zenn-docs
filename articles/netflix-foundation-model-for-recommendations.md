## はじめに

Netflix は 2025 年 3 月から 2026 年 1 月にかけて、レコメンド向け Foundation Model（基盤モデル）に関する技術ブログを 3 本公開しました。

1. Foundation Model for Personalized Recommendation（2025 年 3 月）[^1]
2. Integrating Netflix's Foundation Model into Personalization applications（2025 年 11 月）[^2]
3. Towards Generalizable and Efficient Large-Scale Generative Recommenders（2026 年 1 月）[^3]

Netflix のホーム画面は「Continue Watching」「Today's Top Picks for You」など、複数の推薦面（surface）で構成されています。各推薦面にはそれぞれ専用のモデルが用意されていますが、共通のデータソースを使っているにもかかわらず、多くのモデルは個別に学習・運用されています。その結果、次のような課題がありました。

- レコメンドシステム全体の運用コストが大きい
- あるモデルで得られた改善を、別のモデルへ転用しにくい
- 多くのモデルが、直近の短い行動履歴しか活用できていない

この課題に対して Netflix は、ユーザー嗜好の学習を一元化する基盤モデルを構築しました。背景にあるのは、NLP における LLM の成功です。特に、以下の 2 つの考え方が推薦システムにも応用されています。

1. **データ中心のアプローチ**
   タスクごとの特徴量エンジニアリングに依存するのではなく、大規模かつ高品質な行動データから汎用的な表現を学習する。
2. **半教師あり学習の活用**
   LLM の Next-Token Prediction のように、明示的なラベルがない大量のユーザー行動履歴を事前学習に利用する。

本記事では、これら 3 本のブログをもとに、Netflix のレコメンド基盤モデルについて以下の観点で整理します。

- 基盤モデルのアーキテクチャ
- 長いユーザー履歴を扱うための工夫
- Multi-Token Prediction による目的関数の改善
- スケーリング則と学習・推論の効率化
- 本番システムへの 3 つの統合パターン
- コールドスタートへの対応

### ユーザーインタラクションのトークン化

Netflix では、ブラウジング、検索、再生、一時停止、視聴完了など、さまざまなユーザーインタラクションが発生します。これらをそのまま Transformer に入力すると、系列長が長くなりすぎるだけでなく、ノイズも多くなります。

そこで Netflix は、ユーザー行動履歴を **トークン化** します。これは NLP における Byte Pair Encoding（BPE）に似た発想です。隣接する細かいアクションをまとめ、より高レベルな意味を持つイベントトークンへ圧縮します。

たとえば、同一タイトルに対する「再生開始」「一時停止」「再開」「停止」といった複数のイベントを 1 つのトークンにまとめます。ただし、単に圧縮するだけではなく、視聴時間、インタラクション種別、発生時刻、デバイス、タイトルのメタデータといった重要な情報は保持します。

![ユーザーインタラクション履歴のトークン化](/images/netflix-foundation-model-for-recommendations/tokenization_of_user_interaction_history.webp)
*ユーザーインタラクション履歴のトークン化*

このトークン化には、次のような効果があります。

- 冗長なイベントを減らし、系列長を短くできる
- ユーザーの意図を表す意味のある単位で学習できる
- 異なる種類の行動を、同じ系列モデリングの枠組みで扱える

一方で、圧縮しすぎると細かな行動情報が失われます。逆に粒度を細かくしすぎると系列長が伸び、学習・推論コストが増大します。つまり、トークン化は単なる前処理ではなく、推薦品質と計算効率のトレードオフを決める重要な設計要素です。

### 長系列への対応

トークン化で圧縮しても、アクティブなユーザーのインタラクション系列は非常に長くなります。標準的な Self-Attention は系列長に対して計算量が二乗で増えるため、そのままでは実用的ではありません。

さらに、推薦システムでは LLM の対話生成のように数秒待つことは許容されにくく、ミリ秒単位のレイテンシが求められます。そこで Netflix は、長い履歴を扱うために複数の工夫を組み合わせています。

#### Sparse Attention

Self-Attention の全組み合わせを計算するのではなく、低ランク近似などを活用して計算量を抑えます。これにより、より長いユーザー履歴を扱いながら、推論コストを現実的な範囲に保つことができます。

#### Sliding Window Sampling

学習時には、ユーザー履歴全体を一度に入力するのではなく、重なり合う window をサンプリングします。複数 epoch にわたって異なる window を見ることで、巨大な context window を使わずに、長期的な行動履歴のさまざまな部分から学習できます。

#### KV Cache

推論時には、過去の Key / Value をキャッシュして再利用します。ユーザーの直近の行動だけを追加で処理すればよくなるため、長い履歴に対しても低レイテンシで推論しやすくなります。

これらの工夫により、モデルは直近の短期的な行動だけでなく、過去の長期的な嗜好も取り込めるようになります。

## 目的関数の設計

基本的な学習の枠組みは、GPT と同様の自己回帰型 Next-Token Prediction（NTP）です。ユーザーの過去のインタラクション系列を入力し、次に起きるインタラクションを予測します。

ただし、言語モデルと推薦モデルでは、予測対象の性質が大きく異なります。

言語では、次の単語の順序が非常に重要です。一方、推薦では「ユーザーが次に何を好みそうか」を予測したいのであり、必ずしも 1 つの正解順序に絞れるとは限りません。また、すべてのインタラクションが同じ重要度を持つわけでもありません。5 分間の予告編再生と 2 時間の映画視聴では、ユーザー嗜好に対する情報量が異なります。

この違いを踏まえ、Netflix は目的関数にいくつかの拡張を加えています。

### Multi-Token Prediction（MTP）

標準的な NTP では、直後の 1 トークンだけを予測します。一方、Multi-Token Prediction（MTP）では、将来の一定時間窓に含まれる複数のアイテムを予測対象にします。

MTP が必要になる理由は、大きく 2 つあります。

#### 1. サービング時のレイテンシとのミスマッチ

本番環境では、推薦結果や embedding がキャッシュされ、数分から数時間遅れてユーザーに提示されることがあります。この場合、学習時に「次の 1 アイテム」として扱った対象が、実際に推薦を表示するタイミングではすでに古くなっている可能性があります。

たとえば、あるユーザーの履歴からタイトル A を次に視聴すると予測したとしても、キャッシュの遅延により、ユーザーが推薦を見る頃にはすでに A を視聴済みかもしれません。その時点で必要なのは、A ではなく、その次に視聴しそうなタイトル B の推薦です。

![レイテンシ条件別の MRR 劣化](/images/netflix-foundation-model-for-recommendations/mrr_degration.webp)
*レイテンシ条件別の MRR 劣化*

Netflix の実験では、長期的な嗜好を問うタスクはレイテンシの影響を受けにくい一方、短期的な依存が強いタスクでは性能劣化が大きいことが示されています。

#### 2. 推薦対象の順序不変性

推薦では、将来ユーザーが関心を持つアイテムの集合が重要で、厳密な順序は重要でないケースがあります。たとえば、ユーザーが A と B のどちらにも興味を持つなら、A → B でも B → A でも、推薦としては妥当です。

しかし NTP は単一の順序にコミットするため、同じくらい妥当な別の順序に対してもペナルティを与えてしまいます。

MTP では、将来の時間窓に含まれるアイテムをマルチラベルの集合として扱い、時間的に近いものほど大きな重みを与えます。損失関数は、概念的には次のように表せます。

$$
\mathcal{L} = \sum_{\text{label}} \text{Reward}(\text{label}) \cdot e^{-\beta \cdot \Delta t} \cdot \text{CrossEntropy}(\text{label})
$$

ここで、$\text{Reward}(\text{label})$ は視聴時間、完了率、新規性、多様性などの効用シグナルを表します。$\Delta t$ は現在の文脈から対象ラベルまでの時間差、$\beta$ はキャッシュの更新間隔に合わせて調整する減衰パラメータです。

重要なのは、MTP が単に「複数ステップ先まで逐次デコードする」わけではない点です。単一のデコーディングヘッドを維持し、カタログ全体に対する logits を 1 パスで計算したうえで、ラベル集合に対する重み付き cross-entropy として最適化します。

![MTP vs NTP の比較](/images/netflix-foundation-model-for-recommendations/mtp_comparison_ntp.webp)
*MTP vs NTP の性能比較*

高レイテンシ環境（48 時間遅延）では、MTP はすべてのタスクで大きく改善しています。オンライン環境（p95 レイテンシ < 1 秒）でも、順序不変性の高いタスクでは改善が見られます。一方で、短期的な順序依存が強いタスクでは、MTP によってわずかに性能が下がる場合もあります。

つまり MTP は、すべてのケースで NTP を置き換える万能な目的関数ではなく、サービング形態や推薦面の性質に応じて有効性が変わる手法といえます。

### 補助的な目的関数

アイテム ID の予測だけでは、人気アイテムや一時的なトレンドに過度に引っ張られる可能性があります。そこで Netflix は、ジャンルなどの抽象的な属性を予測する補助目的も導入しています。

たとえば、ユーザーが次に視聴しそうなタイトル ID だけでなく、そのタイトルのジャンルも予測します。これにより、モデルは個別アイテムに閉じた表現ではなく、ユーザーのより抽象的な嗜好を学習しやすくなります。

補助目的には、以下のような効果が期待できます。

- item ID への過学習を抑える正則化効果
- ユーザーの長期的なジャンル嗜好の獲得
- item ID 予測の精度向上
- 新規タイトルや低頻度タイトルへの汎化

## スケーリングと効率化

### レコメンドにおけるスケーリング則

Netflix は、モデルサイズを 50M パラメータ規模から 1B パラメータ規模まで拡大し、推薦タスクにおいてもスケーリング則が成り立つかを検証しています。

結果として、LLM と同様にモデルサイズの拡大に伴って性能が向上する傾向が確認されました。ただし、推薦タスクではユーザー行動に本質的な不確実性があるため、性能が無限に伸び続けるわけではありません。そこで、Netflix は切片項 $P_0$ を持つスケーリング則で性能を近似しています。

$$
P = P_0 - aN^{-b}
$$

ここで、$N$ はモデルパラメータ数、$P$ は性能指標、$P_0$ はそのタスクで到達しうる性能上限を表します。

たとえば、あるタスクでは $P_0 = 0.311$ であり、モデルを大きくしても MRR は 0.311 に漸近すると解釈できます。一方、別のタスクでは $P_0 = 1.075$ と推定されています。MRR の上限は 1 なので 1 を超える部分は推定誤差ですが、このタスクは十分にスケールすればほぼ完全に近い精度へ到達しうる、という見方ができます。

![タスク別のスケーリング則](/images/netflix-foundation-model-for-recommendations/scaling_law.webp)
*タスク別の MRR スケーリング則*

この $P_0$ は、単なるフィッティングのためのパラメータではなく、タスクの難易度を定量化する指標としても有用です。性能上限が低いタスクに対してモデルサイズだけを増やしても、投資対効果は限定的かもしれません。逆に、上限が高く、まだ伸びしろがあるタスクには、モデルサイズやデータ量を増やす価値があります。

:::message
評価指標には MRR（Mean Reciprocal Rank）が使われています。Hit Rate や NDCG などの指標ではモデル間の漸進的な差が見えにくい場合があるため、連続的な改善を捉えやすい MRR が選ばれています。
:::

### 学習・推論の効率化

推薦基盤モデルの効率化は、LLM とは少し違う難しさがあります。

LLM は一度大規模に学習したモデルを比較的長期間使い続けることができます。一方、推薦モデルはユーザー嗜好やコンテンツカタログの変化に追従する必要があるため、定期的な再学習や fine-tuning が欠かせません。

さらに、推薦システムでは出力語彙に相当するカタログサイズが非常に大きくなります。Netflix のブログでは、Netflix のカタログサイズは GPT-3 の語彙サイズの約 40 倍であり、2 兆トークンを定期的に処理していると説明されています。

このとき特に問題になるのが、デコーディングコストです。LLM の語彙サイズはおおよそ 10 万トークン規模ですが、推薦システムでは数百万から数十億のエンティティを扱う可能性があります。語彙サイズが大きくなると、最終層で全アイテムに対する logits を計算するコストが支配的になります。

![語彙サイズと Training FLOPs の関係](/images/netflix-foundation-model-for-recommendations/flops.webp)
*語彙サイズと Training FLOPs の関係*

Netflix はこの課題に対して、主に 2 つの手法を使っています。

#### Sampled Softmax

学習時にカタログ全体へ logits を計算するのではなく、サンプリングした負例候補に対してのみ計算します。これにより、実効的な語彙サイズを小さくできます。

#### Projected Head

penultimate layer の出力をそのまま大きな出力層へ接続するのではなく、活性化関数と線形射影を挟み、より小さな次元へ圧縮してから logits を計算します。これにより、デコーディング部分の計算量を削減できます。

Sampled Softmax と Projected Head を組み合わせることで、学習コストを 1〜2 桁削減できると報告されています。また、Netflix の現行インフラでは、80 台の A100 GPU（80GB）で 240 時間 / cycle の学習を定期的に実行し、さらに頻繁な fine-tuning も行っています。

### Embedding の安定化

基盤モデルを再学習すると、ランダム初期化の影響により embedding 空間が大きく変わります。また、前日のモデルから warm-start して日次で fine-tuning しても、embedding は少しずつドリフトします。

下流モデルが基盤モデルの embedding を特徴量として利用している場合、embedding 空間が変わるたびに下流モデルも再学習しなければならなくなります。これは本番運用上、大きな負担です。

この課題に対して Netflix は、**Orthogonal Low-Rank Embedding Stabilization** を用いています[^4]。毎日生成される embedding を同一の embedding 空間へマッピングすることで、下流モデルが embedding を安定した特徴量として利用し続けられるようにしています。

## 本番システムへの 3 つの統合パターン

Netflix は、基盤モデルを下流の推薦アプリケーションへ統合する方法として、以下の 3 パターンを実験し、いずれも本番環境で利用しています。

1. Embeddings パターン
2. Subgraph パターン
3. Fine-tuning パターン

重要なのは、この 3 つが単なる代替案ではない点です。推薦面ごとに、レイテンシ要件、技術スタック、求める鮮度、基盤モデルをどこまで活用したいかが異なります。そのため、制約に応じて適切な統合方法を選べるようにしています。

### Embeddings パターン

Embeddings パターンでは、基盤モデルからユーザー embedding とアイテム embedding をバッチ生成し、Embedding Store に保存します。各アプリケーションは、この embedding を特徴量として利用します。

Netflix では、以下のような更新サイクルを採用しています。

1. 月次で基盤モデルを事前学習する
2. 最新データを使って日次で fine-tuning する
3. 新規タイトルの entity ID も日次 fine-tuning で追加する
4. fine-tuning 後にバッチ推論を実行し、profile / item embedding を更新する
5. 更新した embedding を Embedding Store へ公開する

![Embedding Store 統合フロー](/images/netflix-foundation-model-for-recommendations/embedding_store_integration.webp)
*Embedding Store 統合フロー*

Embedding Store は、embedding のバージョニングやタイムスタンプ管理を担い、オフライン・オンラインの両方から利用できるインターフェースを提供します。

この方式の利点は、導入コストが低いことです。既存の推薦モデルに対して、基盤モデルの embedding を特徴量として追加すればよいため、既存パイプラインを大きく作り替える必要がありません。また、candidate generation や title-to-title recommendation などにも利用できます。

一方で、embedding はバッチ更新であるため、鮮度に課題があります。セッション中のユーザー行動を即座に反映したいユースケースでは、基盤モデルの価値を十分に引き出せない可能性があります。

Netflix はこの課題に対処するため、ニアリアルタイム embedding 生成フレームワークにも投資しています。これにより、セッション中のユーザーアクションに基づいて embedding を更新し、下流モデルをより適応的にすることを目指しています。

### Subgraph パターン

Subgraph パターンでは、基盤モデルのデコーダスタックを下流モデルの計算グラフの一部として組み込みます。事前計算された embedding を使うのではなく、リクエスト時に基盤モデルのサブグラフを実行し、その出力を ranking などの下流モデルへ渡します。

![Subgraph 統合](/images/netflix-foundation-model-for-recommendations/subgraph_integration.webp)
*Subgraph 統合*

この方式では、基盤モデルの推論と下流モデルの推論の間にタイムラグがないため、最新のユーザー行動を反映しやすくなります。また、Embedding Store に公開されている最終 embedding だけでなく、中間層の表現も利用できます。

一方で、基盤モデルの一部を下流推論に持ち込むため、特徴生成や推論パイプラインは複雑になります。モデルサイズや推論時間も増加します。

Netflix では、サブグラフを profile ごとに 1 回だけ実行し、その結果をリクエスト内の全アイテムで共有することで、推論コストを抑えています。

### Fine-tuning パターン

Fine-tuning パターンでは、基盤モデルを推薦面固有のデータや目的関数で fine-tune し、その推薦面専用のモデルとして直接利用します。

たとえば、「Trending Now」のような推薦面では、最近トレンドになっているタイトルへのインタラクションを重視したいかもしれません。一方で、別の推薦面では、ユーザーの長期的な嗜好をより重視したい場合もあります。

![Fine-tuned FM 統合](/images/netflix-foundation-model-for-recommendations/fine_tuned_integration.webp)
*Fine-tuned FM 統合*

fine-tuning では、全パラメータを更新するだけでなく、一部レイヤーを凍結したり、別の出力ヘッドを追加して異なる目的関数で最適化したりできます。

この方式の利点は、推薦面ごとの要件に最も深く適応できることです。また、新しい推薦面を立ち上げる際に、ゼロからモデルを設計するのではなく、基盤モデルを fine-tune することで強力なベースラインを得られます。

一方で、推薦面ごとに fine-tuned モデルや運用パイプラインが増えるため、保守・運用コストは高くなります。レイテンシや SLA も推薦面ごとに最適化する必要があります。

### 3 パターンの比較

| パターン | 導入コスト | 鮮度 | 表現力 | 運用負荷 | 向いているユースケース |
| --- | --- | --- | --- | --- | --- |
| Embeddings | 低い | バッチ更新のため低い | 最終 embedding のみ | 低い | 既存モデルへの特徴量追加、candidate generation |
| Subgraph | 中程度 | 高い | 中間層も活用可能 | 中程度 | 最新行動を反映した ranking、高インパクトな推薦面 |
| Fine-tuning | 高い | 目的に応じて調整可能 | 最も高い | 高い | 推薦面固有の目的関数を強く反映したい場合 |

実務的には、まず Embeddings パターンで低コストに導入し、効果や鮮度の課題を見ながら Subgraph や Fine-tuning に進む、という段階的な導入が自然だと感じました。

## コールドスタートへの対応

推薦システムでは、新しいアイテムがカタログに追加された直後から、そのアイテムを誰に推薦すべきかを判断する必要があります。しかし、新規タイトルには十分なインタラクション履歴がありません。これは典型的なコールドスタート問題です。

Netflix はこの問題に対して、複数のアプローチを組み合わせています。

### Incremental Training

基盤モデルは全ユーザーの行動履歴を使って学習するため、新規タイトルが追加されるたびにゼロから再学習するのは現実的ではありません。

そこで、前回のモデルパラメータを再利用し、新規タイトルに関するパラメータだけを初期化する warm-start 方式を採用しています。新規タイトルの embedding は、既存タイトルの平均 embedding に小さなノイズを加えたり、メタデータが類似するタイトルの embedding を加重平均したりして初期化します。

### メタデータ embedding の活用

タイトルには、ジャンル、ストーリーライン、トーンなど、さまざまなメタデータが紐づいています。Netflix はこれらのメタデータ embedding を組み合わせ、タイトルの metadata embedding を構成します。

最終的なタイトル embedding は、metadata embedding と学習可能な ID embedding を混合して生成されます。ここで重要なのは、単純に加算するのではなく、エンティティの **age**、つまり公開からの経過時間に応じて重みを変える点です。

新規タイトルではインタラクションデータが少ないため、metadata embedding の重みを大きくします。十分なインタラクションが蓄積されたタイトルでは、学習済みの ID embedding の重みを大きくします。

![メタデータ embedding の構成](/images/netflix-foundation-model-for-recommendations/metadata_embedding.webp)
*メタデータ embedding の構成*

さらに、学習時に ID embedding をランダムにマスクすることで、メタデータだけからアイテムの特徴を推論する能力を高めています。

### Multi-modal Semantic Tower

さらに発展した取り組みとして、視覚情報（ボックスアート）、言語情報（あらすじ）、ナレッジグラフなどを統合する **Multi-modal Semantic Tower** が導入されています。

![Semantic Item Tower](/images/netflix-foundation-model-for-recommendations/semantic_item_tower.webp)
*Semantic Item Tower のアーキテクチャ*

Semantic Tower は、各モダリティの特徴量を専用モデルで embedding 化し、それらを generative recommender に入力します。学習可能な collaborative embedding と semantic tower の出力を加重和で統合することで、encoding と decoding の両方にセマンティック情報を注入します。

学習時には、collaborative embedding をランダムに OOV embedding でマスクします。これにより、モデルはセマンティック情報だけからアイテムの性質を推論する能力を獲得します。マスク確率は、学習からサービングまでの時間差によって発生するコールドスタートアイテムの出現確率に合わせて設定されています。


## おわりに

Netflix の 3 本のブログからは、推薦システムにおける大規模 Transformer 活用の実践的な工夫を多く学べました。

個人的には、特に実務で参考にしやすいのは、Sliding Window Sampling と MTP だと感じました。Sliding Window Sampling は、長い行動履歴を持つアクティブユーザーを扱ううえで導入しやすく、MTP は推薦結果のキャッシュやバッチ更新が避けられないシステムにおいて、学習とサービングのミスマッチを減らす有効な考え方です。

また、スケーリング則に切片項 $P_0$ を導入してタスクごとの性能上限を見積もる発想も面白いです。単にモデルを大きくするのではなく、どのタスクに計算資源を投資すべきかを判断する材料になります。

推薦システムにおける基盤モデルは、まだ LLM ほど一般化されたベストプラクティスが確立している領域ではありません。その意味で、Netflix の事例は「大規模モデルをどう作るか」だけでなく、「既存の本番推薦システムへどう統合するか」を考えるうえでも非常に参考になる内容でした。
