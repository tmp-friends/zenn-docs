# 日本語技術記事のブラッシュアップ

著者が伝えたい技術上の主題と語り口を保ち、具体的な実装・判断理由・結果が自然につながる記事に整える。情報量を増やすことより、この記事を読んで何がわかるかを明確にする。

## 編集の基準を定める

- 対象記事と、ユーザが指定した推敲済みの参考記事を全文読む。既存の差分と最新の指示を確認し、ユーザの編集を保つ。
- 参考記事から、説明の順序、文の長さ、用語の粒度、具体例の使い方、著者の所感の書き方を読み取る。参考記事の内容や数値は対象記事へ転用しない。
- タイトル・導入・依頼から、記事の中心となる問いを1文で捉え、各章がその問いに答えているか判断する。
- **本文の推敲では既存のタイトルをそのまま保つ。** 語順だけの修正や、章削除に合わせた改題もタイトル変更に含まれる。タイトル変更を依頼された場合に、指定された範囲で扱う。
- Zenn の `emoji`、`type`、`topics`、`published` などのメタデータは、変更依頼がない限り保つ。

ユーザが編集を依頼していればファイルへ反映する。方針への意見だけを求めている場合は、理由と具体的な案を答える。すでに承認された方針での編集について、再び確認を求めない。

## 文体と説明を整える

- 今回の実装を主語にし、「何をしたか」「なぜそうしたか」「どうなったか」をつなぐ。章の順序は読者が理解しやすい流れに合わせ、固定のテンプレートにはめない。
- 「そこで」「今回は」などで、課題と判断をつなぐ。コードや数値を置く前に、その例で何を説明するかを短く示す。
- 「まとめようと思います」「対策を重ねています」などの回りくどい表現は、動作や判断を直接説明する言葉に直す。
- 事実、測定結果、著者の解釈を分ける。所感には、参考記事に合わせて「考えています」「思います」などを使う。
- 箇条書きは手順や並列の項目、表は比較や対応関係に使う。理由や経緯は文章でつなぐ。同じ内容を導入・構成・詳細で繰り返していたら整理する。

例：

> 対策は役割ごとに分けて重ねています。

これを、実装に即して次のように具体化する。

> WAF で短時間の連打を抑え、D1 でサイト全体の日次の呼び出し回数を制限しています。

この説明を記事に残すかどうかは、次の主題の判断に従う。

## 補足を主題に合わせる

| 内容の役割 | 編集の判断 |
|---|---|
| 記事の中心となる実装・判断・結果 | 必要な具体例と理由を残す |
| コードや結論を理解するための前提 | 該当箇所の近くで短く説明する |
| 主題と独立した運用・一般論の詳細 | 重複や脱線を減らす。章の削除や別記事への分離は依頼の範囲で行う |
| ユーザが明示した主題・残すよう指定した内容 | その内容を中心に推敲する |

API の呼び出し方が主題なら、呼び出しに必要なバインディング・ゲートウェイ・課金方式と、コードに残る設定引数の意味を、コードの前後に短く残す。運用の詳細な章を削除する場合も、この前提説明は残る本文へ移す。一方、費用管理やプライバシー自体が主題なら、その章を詳しく説明する。特定の話題を一律に削るルールにはしない。

### 章を削除するとき

削除対象の本文と、その内容を説明する関連記述をまとめて整理する。

- 導入の予告、目次、結論に、削除した話題が残っていないか
- 構成図の要素・矢印と、処理手順が残る説明に対応しているか
- 表示文言、フォールバック例、テスト一覧に、説明しなくなった機能の詳細が残っていないか
- 残したコードの必須設定や引数の意味まで、削除した章と一緒に失っていないか
- 「後述」「前述」「別章」などの参照先が存在するか
- 脚注番号・参考文献・リンクが本文と対応しているか
- 同じ出典の脚注を本文中で繰り返さず、複数の主張を支える場合は、対象範囲が分かる箇所に一度だけ置く

記事で扱う範囲を絞る編集として説明し、実際のアプリから機能を削除したかのように書かない。

## 技術的な事実を保つ

- 著者が実際に試したこと、観測した応答、運用実績を新たに創作しない。「API の応答形式」を説明した原稿を、「呼んだときに確認できた」という体験談へ変えない。
- コード例は説明する技術内容を保つ。コード変更が必要なら実装や一次資料と照合し、文章だけから機能を補わない。
- 同じ実験・同じ条件を扱う記事間では数値の整合を確認する。異なる実験の数値を揃えない。見積もりと実測、回数の制限と金額の上限、提供元の仕様と今回の観測を区別する。
- 料金・制限・API 仕様などを検証する場合は、必要な箇所を公式の一次資料で確認し、根拠を近くに付ける。文体の推敲を網羅的な仕様調査へ広げない。
- 根拠より強い断定を、根拠が示す範囲の表現に直す。未確認の値や結果は未確認として扱う。

## 最終確認と報告

差分を読み直し、主題・参考記事の語り口・最新の指示に合っているか確認する。Markdown のコードブロックや脚注、見出し、リンクの対応を確認し、Git のある作業場所では `git diff --check` を実行する。Zenn CLI が利用できる場合は記事情報の読み込みも確認する。

文章の編集を検証するためにアプリのテストを新設しない。アプリを動かしていない場合に、本文に登場するテストやデプロイを今回実施したように報告しない。

最終報告は、編集したファイル、主な変更、実際に行った確認を短く示す。
